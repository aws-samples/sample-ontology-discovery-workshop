# (향후 개발 메모) 런타임 그래프 성능 평가 스킬

> 상태: **보류 / 향후 별도 스킬**
> 관련 문서: `.claude/skills/graph-evaluation/SKILL.md` (정적 모델 품질 평가 스킬)
> 작성 이유: 사용자가 제안한 두 성능 지표는 **실제 데이터가 적재되고 쿼리를 실행해야**
> 산출되는 값이라, "데이터·실행 없이 스키마+인스턴스만 보는" 현재 정적 스킬 범위에
> 들어갈 수 없다. 그 아이디어를 잃지 않도록 여기에 메모하고, 나중에 독립 스킬로 개발한다.

---

## 1. 왜 분리하는가 (범위 구분)

| | 정적 모델 품질 스킬 (현재) | 런타임 성능 스킬 (이 메모) |
|---|---|---|
| 입력 | `workshop-model.json` (tbox+snapshot) | **실제 데이터가 적재된 그래프 DB** + 워크로드 |
| 실행 | 없음 (파일만 분석) | **쿼리 실제 실행 + 시간/처리량 측정** |
| 측정 대상 | 모델 구조 품질 | 엔진·모델이 함께 만들어내는 **실행 성능** |
| 전제 | 데이터 불필요 | **데이터 적재 완료가 선행 조건** |

→ 두 지표(`E_t`, `ΔT`)는 전부 오른쪽(런타임)에 속한다. 그래서 현재 스킬엔 **미포함**,
이 메모의 향후 스킬에서 다룬다.

---

## 2. 선행 조건 (이 스킬을 돌리려면)

1. 평가 대상 그래프 DB에 **실제(또는 대표성 있는) 데이터가 적재**되어 있어야 한다.
2. 측정에 쓸 **고정 워크로드**가 있어야 한다. → 가능하면 워크숍에서 정의한
   역량질문(`queries`)을 그대로 사용(모델이 "답해야 하는 질문"과 일치해 가장 공정).
3. 측정 환경 메타데이터 기록: 엔진/버전, 하드웨어, 데이터 규모(노드/엣지 수),
   그래프 revision. (재현성·비교 가능성 확보)

---

## 3. 지표 1 — 탐색 효율지표 `E_t = T / E_traversed`

- **확정 정의:** `T` = **시간**, `E_traversed` = 해당 쿼리가 **실제 밟은 엣지 수**.
  → `E_t` = **엣지당 평균 소요 시간**(per-edge latency). 낮을수록 좋음.
- **무엇을 재나:** 주로 **DB 엔진의 엣지 처리 효율**(캐시·인덱스·스토리지 지역성).
  모델 품질보다 엔진 성능에 가깝다.
- **반드시 함께 봐야 하는 짝 지표 — `E_traversed` 자체:**
  모델링이 나쁘면 "한 답을 얻으려 쓸데없이 많은 엣지를 밟는" 형태로 나타나는데,
  `E_t`는 그 `E_traversed`로 나눠 **그 신호를 상쇄**한다.

  | | 밟은 엣지 | 시간 | E_t |
  |---|---|---|---|
  | 좋은 모델 | 3 | 3ms | 1 ms/edge |
  | 나쁜 모델(슈퍼노드) | 300 | 300ms | 1 ms/edge |

  두 경우 `E_t`는 동일하지만 실제론 100배 차이. 따라서 **스킬은 `E_t`와
  `질문당 E_traversed`를 항상 쌍으로 보고**해야 한다.
  - `E_t` 낮음 + `E_traversed` 낮음 → 엔진·모델 모두 양호
  - `E_t` 낮음 + `E_traversed` 높음 → 엔진은 빠른데 **모델이 과도 탐색 유발**
  - `E_t` 높음 → 엔진/스토리지 병목 의심

---

## 4. 지표 2 — 평균 정점 차수당 처리량 `ΔT = (T_dense − T_sparse) / (k_dense − k_sparse)`

- **확정 정의:** `T` = **성능(처리량, throughput)**, `k` = 영역의 **평균 정점 차수**,
  `dense`/`sparse` = **한 그래프 내부의 밀/소 영역**.
  → `ΔT` = 평균 차수가 1 늘 때 처리량이 얼마나 변하는가(= 밀도 민감도 기울기).
- **의도:** 그래프 DB가 **고차수(fan-out)/슈퍼노드**에서 성능이 무너지는 정도를 측정.
  착안은 유효하다.
- **부호 유의:** dense 영역은 보통 처리량이 더 낮으므로 `ΔT`는 **대개 음수**.
  관심은 `|ΔT|`(= 차수 증가에 따른 **열화율**). 클수록 density에 취약.

### 4.1 "한 그래프의 밀/소 영역"이라서 생기는 장점과 과제

- **장점:** 같은 엔진·하드웨어·데이터셋에서 측정하므로 하드웨어·엔진 설정·콜드스타트
  같은 교란요인이 상당 부분 통제된다. (서로 다른 두 그래프 비교보다 공정)
- **과제 1 — 영역 정의:** 정점을 차수 기준으로 어떻게 나눌지 명시해야 한다.
  (예: 차수 백분위로 상위 밴드=dense, 하위 밴드=sparse)
- **과제 2 — 경계 횡단:** 탐색이 영역 경계를 넘나들면 측정이 섞인다.
  경계 횡단 엣지를 포함할지/워크로드를 영역 내부로 앵커할지 규칙을 정한다.
- **과제 3 — 캐시 공유:** 같은 세션에서 연속 측정하면 앞 실행이 뒤 실행 캐시를 데움.
  실행 순서 무작위화 + 워밍업 통제로 완화.

### 4.2 권장 개선 — 2점 기울기 → 다중 차수 밴드

- 2점(dense/sparse)만 쓰면 차수-성능 관계의 **비선형 변곡점(절벽)**을 놓친다.
  슈퍼노드 효과는 특정 차수에서 급격히 꺾이는 경우가 많다.
- 또 **평균 차수**는 분포 꼬리(소수 슈퍼노드)를 가린다.
- **개선안:** 정점을 **차수 밴드 여러 개(≥3~5)**로 버킷팅하고, 밴드별 처리량을 측정해
  **곡선/회귀 기울기**를 구하고 **성능이 붕괴하는 임계 차수**를 찾는다.
  - 밴드를 좁게 잡으면 밴드 내 평균 차수가 대표성을 가져 과제 2(평균의 함정)도 완화.
  - `ΔT`(2점)는 이 곡선의 특수 사례로 유지하되, 메인 산출물은 **밴드별 곡선 + 임계 차수**.

---

## 5. 측정 프로토콜 (노이즈·편향 방지)

1. **고정 워크로드**로만 측정(가능하면 `queries` 역량질문).
2. **워밍업 실행** 후 버리고, 본 측정은 **N회 반복**하여 **중앙값/‌p95** 보고(평균은 이상치에 취약).
3. 변수 격리: 동일 엔진·세션, 캐시 상태를 일관되게(모두 콜드 또는 모두 워밍).
4. 각 쿼리에서 **실행 시간 `T`와 밟은 엣지 수 `E_traversed`를 함께** 수집
   (엔진의 쿼리 프로파일/EXPLAIN ANALYZE 류 활용).
5. 환경 메타데이터(2장) 리포트에 포함.

## 6. 정적 스킬에서의 대체 지표 (지금 당장 가능한 것)

데이터·실행 없이도 **같은 의도**를 근사하려면 아래를 정적 스킬에서 계산한다.
(상세는 `.claude/skills/graph-evaluation/SKILL.md`)

- **차수 분포 통계**: 평균 외에 `max`·`p99`·왜도(skew) → 슈퍼노드/고fan-out 위험을
  정적으로 포착(지표 2의 정적 대체).
- **질문당 예상 탐색 엣지 수(estimated E_traversed)**: `queries` 패턴 × 스키마 경로 ×
  인스턴스 카디널리티로 추정 → 지표 1이 지워버린 "모델 과도 탐색" 신호를 되살림.
- **관계 카디널리티/경로 길이**: `N:M` 비율, 질문 경로 홉 수.

→ 정적 스킬은 위 **구조 기반 추정치**로 가고, 실제 `E_t`/`ΔT`는 데이터 적재 후
이 메모의 런타임 스킬에서 **측정값**으로 보완하는 2단 구성이 자연스럽다.

## 7. 향후 스킬 산출물 (일관성 유지)

- 출력은 정적 스킬과 동일하게 **단일 HTML**(오프라인·외부 의존성 없음, 화려한 UI 금지,
  IT 개발자 대상). 섹션 예:
  1. 환경·워크로드 요약
  2. 쿼리별 `E_t`와 `E_traversed` 쌍 테이블 + 해석(3.0 분류)
  3. 차수 밴드별 처리량 곡선 + 임계 차수(지표 2 개선판)
  4. 정적 스킬 추정치와의 대조(예측 vs 실측 편차)
